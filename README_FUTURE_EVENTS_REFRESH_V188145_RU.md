# GIGORAVE V188.145 — полное обновление сохранённых будущих тус

## Команда владельца в ЛС

`тусы обновить будущие`

Это отдельный ЯВНЫЙ проход по уже сохранённым будущим карточкам с исходными HTTP/HTTPS-ссылками. Он **не** открывает все посты интернета, не является автоматическим фоновым `парсер все` и не гарантирует картинку там, где нет исходной фотографии или доказанной связи изображения с конкретной тусой. Работает на живой установке с ранее сохранёнными `.env`, `data/` и SQLite.

Порядок выполнения: (1) по базе проверяются сохранённые фотографии с Vision-фактами и ранее отсутствовавшим индексом афиши, при этом нужны локальный файл и точная дата + идентичность конкретного события; (2) отдельно запускается штатный конечный проход настроенной VK-беседы `chat:2000000022`, чтобы получить свежие анонсы и репосты; (3) список будущих событий снова читается из БД, ссылки группируются по каноническому URL; (4) каждая исходная ссылка открывается и полностью обрабатывается ПО ОДНОЙ, между завершением предыдущей и началом следующей пауза **10–15 секунд** (само чтение поста, фото и вызовы Vision работают столько, сколько требуется соответствующей штатной логике); (5) карточки с уже подтверждённым и доступным исходным фото не переписываются при перечитывании ссылки: открываются ВСЕ ссылки будущих карточек, но новая информация и изображение записываются только в карточки, у которых нет такой афиши; защита повторяется непосредственно перед записью в SQLite; (6) извлечённые события и изображения сопоставляются с записью по *точной дате* и подтверждаемой идентичности названия/участников/места; если дата или идентичность расходится, запись не заменяется молча; (7) только при полном успехе обновляется verified snapshot. Существующая `тусы перепарсить ссылки` сохраняет свой прежний параллельный режим.

Важные случаи из присланных логов: у «Провожаем лето» в выдаче 26 сентября при тексте источника 19 сентября — это конфликт дат для ручного разбора, а не основание присвоить картинку карточке с другой датой. «Фестиваль Ива» встретился дважды из двух публикаций; одна карточка имела испорченные поля места и участников. Автоматическое склеивание различных событий только по одному слову/дате не делается; окончательная дедупликация использует существующий реестр. Не используем произвольную картинку из другого источника по совпадению даты: у неё может быть иное событие или иная афиша.

Новый проход использует штатный парсер изображения и Vision. После него спорные привязки, у которых уже сформированы кандидаты и есть локальные файлы, владелец может подтвердить в ЛС командой `тусы картинки на ревью`. Если файл отсутствует, нужно восстановить его штатным захватом источника. Если событие подтверждено, но ни одного относящегося к нему изображения нет, система **не изобретает фото**.

## Диагностика и границы

`data/event-image-review/future-refresh-<дата>/result.json`: неполные карточки, исходные файлы, числа Vision-фактов, провалившиеся ссылки и расхождения дат/идентичности. Подробная трассировка чтения URL и DOM: `data/parser-forensic-archives/<runId>/trace.jsonl`, путь приходит в ответе владельцу. Папка с этими данными содержит исходный текст/DOM; **не публикуй её без проверки на приватные данные**.

Режим long-lived Astra и его полная потоковая трассировка, отсутствие локальной границы ожидания содержательных токенов и защита от повторных платных запросов **не менялись**. Новый код не закрывает чужие вкладки по глобальному stop-handler. Не запускать одновременно с другим ручным парсером. Работа на реальном VK/Telegram и платные Vision вызовы в среде сборки не проводились. Проект без рабочей `.env`, SQLite, WAL/SHM, профиля браузера, `data/`, исходных изображений и логов. Перед установкой сохранить согласованную резервную копию базы и `data/`, остановить бота и распаковать код отдельно от пользовательских данных.

## Уточнение V188.146

При `тусы обновить будущие` браузер открывает каждую уникальную исходную ссылку будущих карточек (если у карточки есть HTTP/HTTPS URL), независимо от наличия фото. Между последовательными ссылками выдерживается случайная пауза **10 000–15 000 мс**. Из одной ссылки могут происходить несколько карточек: каждая сопоставляется по дате и идентичности отдельно. При этом по итогам перепарса изменяется только карточка без подтверждённого доступного исходного изображения; карточка, у которой уже есть такое фото, сохраняет и картинку, и остальные поля. Проверка повторяется в БД, чтобы конкурентный выбор афиши владельцем не оказался перезаписан поздним AI-результатом.

Существующие отдельные команды `тусы парсер все` и `тусы перепарсить ссылки` не менялись. Штатный проход беседы 22 в начале команды остаётся отдельным источником новых сообщений и может сохранять обнаруженные в беседе события по прежним правилам; ограничение «только без фото» применяется к проходу по уже сохранённым исходным ссылкам. К отсутствующим/неподтверждённым фотографиям не подставляется произвольная картинка. Отсутствующие HTTP-ссылки остаются в списке для диагностики, а не считаются открытыми. Текстовый Astra-поток и его таймауты не менялись.

## Дополнение: текст обновляется даже при отсутствии подтверждённой афиши

Только команда `тусы обновить будущие` допускает использовать успешно извлечённый текстовый анонс без подтверждённой картинки для обновления уже существующей карточки **при совпадении даты и идентичности события**. В этом случае картинка не прикрепляется, а карточка попадает в отчёт `unresolvedPosters` и при наличии кандидатов — в ревью владельца. Обычная `тусы перепарсить ссылки` по-прежнему требует подтверждённое изображение и не меняет своих правил. На этапе записи в SQLite повторно проверяются реальный выбранный файл, индекс и Vision-совместимость уже привязанной афиши.

Нельзя гарантировать фото у каждого события без доступного исходного изображения или подтверждения владельцем. Для неполного прохода предыдущий verified snapshot не заменяется. Отдельная беседа 22 использует прежние общие правила парсера, её работа не входит в ограничение записи по исходным ссылкам.
