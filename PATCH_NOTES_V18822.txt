Gigorave V188.22

VK history recovery fix from startup log:
- A VK API call that returns HTTP/API success but an empty message list is no longer trusted blindly.
- Before every CMID batch, the recovery pipeline compares the requested range with direct-source CMIDs already proven by the local VK message archive.
- If VK returns none of the locally-known messages from that exact batch, the method is classified as VK_HISTORY_RECOVERY_FALSE_EMPTY.
- The same broken method is not retried three times, and the bot does not continue scanning tens of thousands of CMIDs through an endpoint that has already proven it cannot see known history.
- Other VK API strategies/clients are attempted; if they are also unusable, the existing authenticated browser recovery is allowed to take over.
- Remapped predecessor-chat rows are excluded from the proof set: only sourcePeerId === current peerId validates current-chat visibility.

Expected effect on the supplied log:
Instead of thousands of lines like
  [VK HISTORY CMID STRATEGY OK] ... received=0 ...
the first batch containing locally-known current-chat CMIDs will fail fast with
  VK_HISTORY_RECOVERY_FALSE_EMPTY
and the recovery pipeline will move to the next real strategy.

Event parser strict-poster/repost fixes from V188.21 are retained.
