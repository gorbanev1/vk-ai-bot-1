V94 — DEEP FIXED-POINT EVENT DEDUPLICATION

Проблема V93
============
В выдаче всё ещё могли остаться буквально повторяющиеся карточки, например:
- TATTOOMO 2026 два раза;
- Мото Што-то! два раза.

Причина: V93 блокировал сравнение по одному eventDate. Два источника одного многодневного события могли хранить разные anchor-даты (например 21 и 23 августа), хотя displayDate у обоих был 21–23 августа. На экране карточки выглядели одинаково, но в comparator до полного сравнения не доходили.

V94: контур 1 без ИИ
====================
1. Date interval evidence
- учитывает eventDate и displayDate;
- понимает ISO, 21.08.26–23.08.26 и "21–23 августа 2026";
- сравнивает пересечение календарных интервалов, а не только одну anchor-date;
- смежные дни допускаются как один многодневный ивент при почти одинаковом названии + сильном совпадении места/состава.

2. Название
- NFKC, регистр, ё/е, пунктуация;
- generic tokens типа концерт/вечеринка/event/gig не являются главным содержанием;
- одинаковое нормализованное название + пересекающиеся даты — жёсткий safety rule против дубля в выдаче.

3. Площадка
- удаляются generic venue tokens;
- сравнивается содержательное ядро площадки и адреса;
- "Тупик" и "Бар Тупик, Проспект Революции 31а" получают сильное совпадение;
- "Rock Bar DIESEL" / "Diesel Bar" также сопоставляются по ядру.

4. Участники
- состав разбивается на отдельных артистов;
- порядок не важен;
- для коротких названий сделан более строгий fuzzy threshold, чтобы Band A и Band B не считались одним участником.

5. Время
- сравниваются все HH:MM;
- двери 18:00 / начало 19:00 совместимы;
- сильный конфликт времени не склеивается только на основании общей площадки.

6. Дополнительный evidence
- overlap описаний и условий входа используется как слабый дополнительный сигнал;
- он не может сам по себе склеить события.

V94: второй контур ИИ
=====================
ИИ вызывается только для verdict=ambiguous первого контура.
Модель получает структурированные поля:
- date/displayDate/eventDays;
- time;
- venue;
- title/alternativeTitles;
- participants;
- price;
- description;
- source.

Ответ только same/different/uncertain + confidence.
Далёкие конфликтующие даты ИИ переопределить не может.

AI merge подтверждённых дублей
==============================
Если группа уже доказана как одно событие, но источники содержат разные полезные данные, отдельный GPT merge получает все источники и собирает одну каноническую карточку:
- название;
- расписание по дням;
- площадку по каждому дню;
- участников;
- цену;
- одно объединённое описание без повторов и конкурсного мусора.

Если GPT merge упал, deterministic merge остаётся рабочим: дубль не возвращается.

Многодневность
==============
Введён eventDays[].
Пример:
21.08.26 · 17:00 — турбаза Астра, Новая Усмань
22.08.26 · 12:00 — турбаза Астра, Новая Усмань

Для "10:00–21:30" на диапазоне 21–23 августа интервал времени считается режимом каждого дня, а не ошибочно распределяется как 21=10:00, 22=21:30.
Для "17:00; 12:00" на двух днях времена могут быть разложены соответственно по дням.

Источники
=========
После объединения mergedSources сохраняет все источники.
В compact-афише, если источников больше одного, выводятся все source URL, а не только один.

Paranoid fixed-point pass
=========================
После двух контуров выполняется до 4 финальных проходов. Очевидный duplicate не может остаться из-за порядка merge/normalization:
- одинаковое нормализованное название + пересекающиеся даты -> merge;
- >=97% title + overlapping date + дополнительный anchor -> merge;
- смежные дни одного многодневного события + одинаковое название + место/состав -> merge.

Регрессии
=========
tests/events/eventDuplicateResolution.test.mjs теперь проверяет:
- BEERBIENT + описательная Telegram-карточка -> одна туса, 2 источника;
- TATTOOMO с разными eventDate внутри одного диапазона -> ровно 1 запись;
- Мото Што-то! -> одна запись и day-by-day schedule;
- AI consolidation объединяет отличающиеся детали;
- разные события с сильным конфликтом времени не склеиваются.
