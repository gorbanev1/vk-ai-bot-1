V96 — CHAT REPOST VISION + LIVE TAB PARSING + VERIFIED EVENT CACHE
Build: events-v96-chat-repost-vision-live-verified-events-cache

ПРОБЛЕМЫ

1. VK-беседа могла видеть только текст верхнего сообщения и пропускать факты внутри репоста.
2. Сообщения, где афиша была только картинкой, отсеивались до AI-классификатора.
3. Browser DOM не всегда отдаёт полные вложения репоста/copy_history.
4. Команда «что на изображении» при reply на репост могла получить сокращённый reply_message без вложенных картинок.
5. «тусы ... кратко» каждый раз запускала тяжёлую GPT-нормализацию/dedupe/summarization, поэтому ответ был медленным.
6. Пользователь хочет, чтобы ручная VK-беседа оставалась живой сколько угодно: прокрутил через час/день — парсер должен разобрать новые видимые сообщения; финал только после закрытия вкладки.

1. VK CHAT: ДВА СЛОЯ СБОРА EVIDENCE

Первый слой — браузерный DOM:
- текст сообщения;
- текст вложенного Repost/WallPost/PostContent;
- ссылки;
- img currentSrc/src/data-src/data-original/srcset;
- picture/source srcset;
- CSS background-image;
- фильтрация avatar/icon/reaction/sticker;
- image-only message больше не отбрасывается.

Второй слой — VK API без AI:
- для каждого нового conversation_message_id выполняется hydration через messages.getByConversationMessageId;
- извлекаются nested attachments, forwarded messages, wall и copy_history;
- для wall attachments собираются owner_id/post_id и при возможности выполняется wall.getById;
- из API-ответа добавляются полный текст вложенного поста, source links и изображения максимального размера;
- hydration происходит ДО event-candidate gate. Поэтому если DOM не показал картинку, но она есть во вложенном VK-post, сообщение всё равно становится visual candidate.

Только после этого запускается AI extraction, если есть event-like text или visual evidence.

2. IMAGE/Flyer VISION ДЛЯ СОБЫТИЙ

Если у сообщения есть хотя бы одна содержательная картинка:
- normal text-model extraction не используется;
- изображения (до 8) передаются штатной OpenAI-compatible vision chain;
- промпт требует считать название, дату, время, место, участников, цену/вход прямо с афиши;
- visual_text возвращается как фактическое evidence;
- strict validator проверяет событие по объединённому text + hydrated repost text + visual_text;
- найденные картинки сохраняются вместе с source message/event.

GigaChat в этом маршруте не используется.

3. «ЧТО НА ИЗОБРАЖЕНИИ» НА REPLY К VK-REPOST

resolveRichIncomingImageTargets теперь не останавливается на одной preview-картинке из webhook.
Для VK он объединяет:
- direct/reply images;
- hydrated reply через messages.getByConversationMessageId или getById;
- nested wall/copy_history images;
- full wall post через wall.getById, если доступно.

До 8 уникальных изображений идут в обычный vision pipeline. Это покрывает reply на сообщение, в котором находится репост поста с одной или несколькими афишами.

4. LIVE VK-БЕСЕДА: ПАРСИНГ ЗАКАНЧИВАЕТСЯ ТОЛЬКО ПРИ ЗАКРЫТИИ ВКЛАДКИ

Ручной запуск:
Гигорейв парсер chat:<peer_id>

Поведение:
- вкладка открывается один раз;
- initial backfill идёт постепенно, VK_CHAT_SCROLL_BATCH_MESSAGES=10 по умолчанию;
- размер движения рассчитывается примерно по высоте 10 реально отрисованных сообщений, а не как произвольный прыжок страницы;
- после каждой прокрутки ждётся lazy-media;
- найденные сообщения ставятся в последовательную processing queue;
- после initial backfill live monitor НЕ заканчивается;
- каждые VK_CHAT_LIVE_POLL_MS миллисекунд проверяется текущий DOM;
- периодически выполняется media settle для картинок, появившихся позже;
- пользователь может вручную прокрутить беседу через час/день — новые видимые сообщения будут обработаны;
- закрытие вкладки/явный stop останавливает live monitor;
- перед финалом бот ждёт messageProcessingQueue;
- только затем вызывает onManualSessionClosed и обновляет verified event snapshot.

5. «ТУСЫ ПРОВЕРИТЬ» = ЕДИНСТВЕННЫЙ ТЯЖЁЛЫЙ РУЧНОЙ ПРОХОД

Owner command:
Гигорейв тусы проверить

Она выполняет:
1) чтение всех raw events из текущей БД;
2) GPT normalization;
3) V95 authoritative date/time + complete-link deterministic/two-contour dedupe;
4) GPT только для ambiguous/merge consolidation;
5) compact mini summaries;
6) атомарную запись data/event-verified-snapshot.json.

При старте приложения этот pipeline НЕ вызывается.

6. БЫСТРЫЕ ЗАПРОСЫ АФИШИ

Обычные запросы:
Гигорейв тусы август кратко
Гигорейв тусы сентябрь

больше не запускают сетевой AI-dedupe/normalization/summarization.
Они читают готовый event-verified-snapshot.json из памяти/диска и применяют текущий blacklist на чтении.
Лог:
[PUBLIC EVENTS ROUTE] ... snapshot=verified aiOnRequest=false

Если snapshot ещё ни разу не создан, используется быстрый deterministic fallback без сетевого AI. Рекомендуемый первый шаг после установки: «Гигорейв тусы проверить».

7. АВТОПРОВЕРКА ПОСЛЕ ПАРСИНГА

- одиночный публичный VK/Telegram источник: snapshot обновляется после завершения прохода;
- «парсер все» без активных VK-бесед: snapshot обновляется в конце;
- «парсер все» с VK-беседами: полный verification НЕ запускается посреди live-парсинга; он откладывается до закрытия последней активной вкладки беседы;
- при закрытии одной беседы бот сначала дожидается её processing queue; если другие беседы ещё открыты, пишет EVENT VERIFY DEFERRED;
- после закрытия последней активной VK-беседы запускается один общий verified snapshot pass.

Таким образом «парсер все» больше не означает, что открытая VK-беседа закончила парсинг. В итоговом сообщении отдельно указывается число активных VK-бесед. Это также не запускает несколько тяжёлых AI-проверок подряд при закрытии нескольких чатов.

8. PERSISTENCE

Файл:
data/event-verified-snapshot.json

Хранит canonical event + compactSummary + ticketLink и статистику проверки.
Пишется атомарно через temporary file + rename.
Исходные raw rows разных источников не уничтожаются: provenance Telegram/VK/VK-chat сохраняется для mergedSources.
Blacklist применяется поверх snapshot при чтении, поэтому удалить/вернуть тусу можно без полной AI-перепроверки.
