# GIGORAVE V188.133 — длинные ответы Telegram + /cfprobe для AI-роутера

Это **накопительный патч** поверх ранее предоставленной V188.128, V188.129, V188.130 или V188.131, а не самостоятельная чистая установка. Включает ранее подготовленные V188.129–V188.131, проверку качества событий/слепка, изменения маршрутизации Astra, V188.132 (отправка длинных ответов Telegram) и V188.133 (диагностика /cfprobe). Не содержит баз SQLite, `.env`, пользовательских файлов, ключей или данных чатов. Не устанавливайте два разных патча поверх запущенного бота одновременно.

## Перед установкой

1. Дождитесь завершения текущего TXT-задания, если оно работает. Если обработка уже прервалась, сначала сохраните ВСЮ рабочую директорию проекта, в частности `.env`, базу, `data/astra-text-jobs`, `data/telegram-text-transfer-logs`, `data/logs` и выходные документы. Не удаляйте эти каталоги.
2. Штатно остановите бот. Создайте резервную копию кода отдельно от копии данных и конфигурации.
3. Распакуйте архив поверх исходной структуры проекта V188.128–V188.131, с заменой одноимённых файлов **без удаления остальных файлов и каталогов**. Не переносите ZIP в рабочую директорию как единственный проект.
4. Запустите `npm run test:v188133`, затем штатно запустите бот. Тесты выполняют изолированную симуляцию сервисов; не вызывают реальную платную модель или рабочий Telegram.

## Как использовать прямо из Telegram (только владелец, только личный чат)

`/cfprobe help` — справка. `/cfprobe status` — локальный статус диагностического теста. `/cfprobe log` — получить обычный текстовый файл последней проверки. `/cfprobe stop` — остановить ТОЛЬКО диагностический тест (на стороне роутера вычисление может продолжаться).

**Основной тест реального AI-роутера без ручного создания скрипта или URL:**

`/cfprobe live-stream ПОДТВЕРЖДАЮ`

Он автоматически берёт уже настроенный основной AI-роутер и его credential, делает один новый потенциально платный Chat Completions POST в режиме `stream:true` к настроенной базовой модели (`GPT_MODEL_DEFAULT`). Сообщает в Telegram время до заголовков и первого байта, максимальную паузу между полученными байтами, количество SSE-комментариев heartbeat, data-событий, HTTP-статус и факт получения завершающего `[DONE]` или `response.completed`. После окончания отправляет в Telegram отдельный TXT-файл журнала. Текст ответа модели, ключи и содержимое исходных документов в журнал не записываются.

**Для попытки получить паузу дольше двух минут:**

`/cfprobe live-stream-long ПОДТВЕРЖДАЮ`

Это отдельный, потенциально дорогой запрос к настроенной модели `GPT_MODEL_PRO2` (либо стандартному резервному имени) с `reasoning_effort:high`. Пауза >120 с и наличие heartbeat **не гарантируются**. Диагностическое ожидание этого теста ограничено 210 секундами; это ограничение ТОЛЬКО теста, абсолютные ограничения обычных TXT-заданий не возвращаются. После остановки теста результат исходного AI-запроса может остаться неопределённым: новый POST автоматически не выполняется.

`/cfprobe all-live ПОДТВЕРЖДАЮ` запускает последовательно ДВА независимых потенциально платных теста (stream и non-stream); они не являются повтором друг друга, но для обычного определения heartbeat этот режим не требуется. Неподтверждённые команды с окончанием `live-...` запросы НЕ отправляют.

**Бесплатные test-origin режимы:** `/cfprobe stream`, `/cfprobe sync`, `/cfprobe body`, `/cfprobe h2ping`, `/cfprobe ws`, `/cfprobe async`; `/cfprobe all` проходит их последовательно. Они используют только `CF_PROBE_*_URL` тестового сервера, если такие URL когда-нибудь настроены. При их отсутствии безопасно выводят `SKIPPED` без AI-запросов. Нельзя рассчитывать, что бот автоматически создаст сервер за Cloudflare. Тестовый WS `ping` является ping **прикладного уровня**, а H2 PING — транспортным: они не подтверждают периодические байты ответа исходного AI POST. Асинхронный режим требует отдельно существующих тестовых `create`/`status` endpoint; он не выдумывает jobId и не делает повторный POST.

В .env при желании можно задать только отдельные тестовые URL: `CF_PROBE_STREAM_URL`, `CF_PROBE_SYNC_URL`, `CF_PROBE_BODY_URL`, `CF_PROBE_H2_URL`, `CF_PROBE_WS_URL`, `CF_PROBE_JOB_CREATE_URL`, `CF_PROBE_JOB_STATUS_URL` (`{jobId}` в статусном URL). Для основного `/cfprobe live-stream` ничего из этого добавлять не надо.

Логи создаются отдельно: `data/logs/cloudflare-probes/probe-*.txt`. После завершения теста бот сам пытается отправить журнал TXT-вложением в Telegram; `/cfprobe log` повторно отправляет **сохранённый файл**, не перезапуская AI. Во время теста владелец получает краткую сводку каждые 30 секунд. Внимание: эти уведомления не являются данными исходного AI-соединения и не продлевают его.

## Что меняется в доставке длинного текста Telegram

Длинный готовый ответ делится без потери символов на сообщения до ~3500 UTF-16 единиц с нумерацией и строго последовательной отправкой через Telegram Bot API. Если одна из частей отклонена определённым `429 retry_after`, повторяется ТОЛЬКО эта заведомо отклонённая Telegram-отправка, не AI POST. Если состояние доставки очередной части неоднозначно, бот не повторяет её вслепую. Если часть streaming-ответа уже дошла, а очередная Telegram-операция завершилась ошибкой, бот не перепечатывает весь поток заново — пытается прислать **полный готовый ответ** отдельным TXT-файлом, не перегенерируя ответ модели. Возможность сети Telegram принять этот документ отдельно всё равно должна быть проверена на рабочем окружении.

## Ограничения и честная интерпретация теста

`stream:true` без реальных байтов от роутера не предотвращает Cloudflare 524. Ни этот патч, ни TCP keepalive/H2 PING/streaming тело POST не могут заставить сервер писать heartbeat в **тот же HTTP-ответ**. Наличие SSE-комментариев является признаком активности ответа только на измеряемом участке бот↔Cloudflare↔роутер; не доказывает, что сама модель продолжает вычисление. Если тест завершился раньше двух минут, он не проверил поведение после двухминутной тишины. Отсутствие комментариев не доказывает полное отсутствие heartbeat: роутер может использовать другой формат служебных фреймов; журнал фактических интервалов байтов поможет это различить.

Для гарантированного heartbeat при молчании upstream нужны изменения на стороне роутера с немедленной отправкой SSE и периодической реальной записью без буферизации (см. `docs/ROUTER_SSE_HEARTBEAT_RU.md`); настройки роутера этим ZIP не изменяются. Тесты не запускались против реального роутера: до установки и запуска невозможно подтвердить его поведение.
