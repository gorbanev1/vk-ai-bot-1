# Gigorave V188.136 — forensic trace Astra TXT и восстановление whole-file

Это накопительный ZIP поверх существующего Gigorave (предыдущие кодовые изменения V188.130–V188.135 включены). НЕ содержит `.env`, `data/`, рабочих баз, API-ключей, пользовательских файлов. Он не изменяет сторонний роутер/Cloudflare и не может спасти уже оборванное соединение.

## Исправлено

- Для каждого НОВОГО owner-TXT запроса (Chat Completions и Responses, в том числе `/txt_full`) создан каталог `data/astra-text-jobs/<jobId>/<stage>/attempt-<N>/http-trace/`. В нём:
  - `response.raw.bin` — все байты `fetch Response.body`, фактически прочитанные Node.js, без декодирования текстовым парсером, включая SSE комментарии, ошибочные HTTP body и бинарные/многоязычные данные. При `Content-Encoding` fetch может прозрачно распаковывать тело; файл фиксирует прочитанные Fetch bytes, НЕ пакеты TCP и не роутер-провайдер wire bytes.
  - `events.jsonl` — `request-start`, HTTP статус и безопасные заголовки, каждый body chunk с размером/отступами/gap, `body-eof` или `body-read-error`, SSE типы и факт комментария, исход завершения/ошибка с cause.
  - `request-meta.json` — API, модель, stage, attempt, размер запроса (без prompt и Authorization).
  - `diagnosis.json` — outcome, HTTP, responseId, SHA-256 сырых байтов, их суммарный размер, первичная JS/provider ошибка, elapsedMs; не выдает локальную сетевую диагностику за логи роутера.
- В `transfer.log` выводится `request-trace-ready traceDirectory=...`; `transport-error-detail` содержит источник ошибки, возможный исходный код, факт ручной отмены. Для записи raw диагностики используется backpressure: новые чанки не поступают SSE-парсеру до завершения записи предыдущего; это небольшие дополнительные дисковые операции.
- В Responses SSE различаются `response.failed`, `response.incomplete` и обычное `error`; сохранён reason/код провайдера. `response.incomplete` не считается успешно завершённым отчётом.
- `/txt_status` и startup GET-only recovery распознают `whole-file` наряду с `full`; сохраняется запрет автоматического повторного платного POST. После подтверждённой или неоднозначной Telegram-доставки startup recovery не отправляет ещё один документ автоматически.
- Из `context.send()` правильно извлекается `sent.telegramMessage.message_id` для журнала и delivery state.
- На длительном owner-TXT запросе по-прежнему НЕТ локального idle/absolute abort. `/txt_stop` остаётся ручной остановкой; внешние ограничения Cloudflare/роутера/провайдера сохраняются.

## Применение

**Если действующий запрос ещё идёт — НЕ перезапускать и НЕ отправлять тот же файл снова.** После завершения или выяснения статуса старого задания сохранить резервную копию проекта, `.env`, `data/astra-text-jobs`, `data/telegram-text-transfer-logs`, других рабочих данных. Остановить экземпляр бота и распаковать архив в корень существующего проекта с заменой кодовых файлов. НЕ удалять data/ и не переносить автоматически из ZIP ничего поверх сохранённых журналов.

В корне проекта запустить `npm run test:v188136`, затем штатный запуск. После следующей ошибки вызвать `/txt_log`, найти `request-trace-ready` и исследовать `diagnosis.json`, `events.jsonl` и при необходимости `response.raw.bin` на компьютере бота. `response.raw.bin` содержит ПОЛНЫЙ ОТВЕТ модели и может содержать приватные сведения; файл не пересылается автоматически в Telegram/сторонние сервисы, доступ и срок хранения ограничивает администратор. Не загружать его в общедоступные баг-трекеры без очистки.

Трасса не может определить внутреннюю причину, если роутер/провайдер оборвал TCP без объяснения: для точного вывода в этом случае потребуются логи стороннего сервера по `responseId`, `cf-ray` или client request ID. Локальная диагностика пишет ВСЕ байты, которые прочёл бот, а не те, которые модель успела сгенерировать, но не доставила.

## Что проверено локально

Сценарии имитированного SSE, реального `Response.body`, fragmented UTF-8, SSE comment, внезапного stream error, HTTP 524 body, GET-only recovery `whole-file`, повторной/неоднозначной доставки и status после перезапуска. Проверки реального роутера, полуторачасового запроса и реальной отправки TXT в Telegram этим патчем не выполнялись.
