# GIGORAVE V188.116 — ограниченная проверка совместимости стороннего роутера

Это обновление диагностирует только **способы загрузки файла**; предыдущая V188.115 подтвердила multipart и `?model=` на стороне бота, но НЕ поддержку `POST /files` у стороннего роутера. Исторический 14-пакетный проход из V188.104 передавал распакованный исходный код **текстовыми batch-запросами**, `files=0`. Он НЕ подтверждает Files API, `input_file.file_id` или Code Interpreter.

## Как включить пробу

Сделать резервную копию проекта и состояния; наложить обновление поверх существующей рабочей папки, не удаляя отсутствующих в архиве файлов. Сохранить свои `.env`, API-ключи, данные и БД. Перед запуском задать:

```env
PROJECT_ARCHIVE_ROUTER_PROBE=1
PROJECT_ARCHIVE_ROUTER_PROBE_INFERENCE=0
PROJECT_ARCHIVE_AUDIT_MULTIPASS=0
PROJECT_ARCHIVE_FILES_UPLOAD_VARIANT=auto
```

Перезапустить бота. Отправить минимальный VK ZIP в Telegram **одним документом с подписью-командой аудита**, как раньше. Бот локально принимает, сохраняет и проверяет этот ZIP, но в пробном режиме **не передаёт его содержимое роутеру**. Вместо него он делает крошечный синтетический ZIP с `ROUTER_PROBE.txt` и поочерёдно проверяет до восьми вариантов `POST /files` на том же настроенном базовом URL: стандартный purpose=user_data, multipart model, multipart+query model, query model, multipart+query model_name, multipart model_name, purpose=assistants+model и purpose=assistants. Не изменяет endpoint наугад.

Переходит к следующему варианту только после явного HTTP 400/415/422 без file_id. При 401/403, 404/405, 429, 5xx, сетевом обрыве, неполном ответе или HTTP 2xx без file_id **останавливается**; не считает это явным отказом, позволяющим безопасно отправить следующий запрос. При получении валидного file_id немедленно останавливает перебор. Каждая попытка отправляет **только маленький синтетический ZIP**. При успехе сохраняет **вариант** в `data/audit-jobs/router-file-probe-cache` (ключ хешируется SHA-256 по конфигурации; сам секрет и file_id в кэш не пишутся). Подробный отчёт — `data/audit-jobs/<jobId>/router-probe-report.json`; краткий итог приходит сообщением в Telegram. Синтетический file_id на роутере может остаться: удаление файлов не активировано без подтверждённого DELETE-контракта.

ПРОБНЫЙ режим останавливает основной проектный inference, даже если из-за ошибки был потерян jobId или изменился источник файла. `PROJECT_ARCHIVE_ROUTER_PROBE=1` вместе с MULTIPASS=1 не допускает отправки текстовых batches.

## Отдельная платная мини-проверка

Только ПО ЖЕЛАНИЮ включить `PROJECT_ARCHIVE_ROUTER_PROBE_INFERENCE=1` при `PROJECT_ARCHIVE_ROUTER_PROBE=1`. Если `/files` вернёт file_id, после этого выполняется **ровно один** короткий `POST /responses` с синтетическим файлом и `max_output_tokens=512` для проверки `input_file.file_id`. После любого ответа/обрыва этот тест **не переподключает транспорт и не создаёт второй POST**. Если ответ потерян, оплаченный запрос мог начаться. Наличие file_id не доказывает поддержку Code Interpreter, ZIP-artifact, stream/background или полную идентичность модели. Проба не запускает полный аудит VK ZIP и не возвращает изменённый код.

## После диагностики

Выключить `PROJECT_ARCHIVE_ROUTER_PROBE=0`. Сохранённый вариант `/files` будет выбран при `PROJECT_ARCHIVE_FILES_UPLOAD_VARIANT=auto`, **только если проба вернула file_id**. Пока нет успешной проверки Responses с input_file, не запускайте большой платный SINGLE-SHOT наугад. Ранее успешный способ **текстовых пакетов** доступен отдельно через `PROJECT_ARCHIVE_AUDIT_MULTIPASS=1` и `PROJECT_ARCHIVE_ROUTER_PROBE=0`, но его текущая реализация НЕ гарантирует возобновление всех завершённых пакетов после перезапуска, а один пакет — отдельный платный запрос. Это не автоматический fallback после неудачи /files.

Важная защита: для проектного ZIP при `PROJECT_ARCHIVE_FILES_UPLOAD_VARIANT=auto` **без кэшированного успешного варианта** бот отклонит реальную загрузку до сетевого вызова с кодом `PROJECT_ARCHIVE_FILES_VARIANT_UNCONFIRMED`. Для другого, заведомо совместимого Files API допускается явный выбор `PROJECT_ARCHIVE_FILES_UPLOAD_VARIANT=standard-user-data` (или `legacy` для старого формата V188.115). Это ручное решение оператора, а не доказательство совместимости.

Если все восемь вариантов отвергнуты, вероятно, роутер не реализует совместимый `/files` (или использует иной частный endpoint/контракт). Без документации или рабочего запроса **не добавляем случайные новые URL, методы, JSON/base64 и десятки дорогостоящих inference**.

## Проверки

Новые поведенческие тесты `tests/ai/v188116RouterFileProbe.test.mjs` имитируют HTTP 400 → следующий вариант → file_id, остановку на неопределённом 2xx, 401/403/404/429/5xx/network, исчерпание восьми вариантов без Responses POST, ровно один короткий Responses POST по явному включению и кэш без сохранения API-ключа.

**Это локальная имитация роутера. Реальная совместимость твоего роутера не проверена.**
