# База данных

Проект использует встроенный `node:sqlite`; рабочий файл — `data/bot.sqlite`.

## Правила изменений

- Не включать рабочую базу в patch/archive.
- Перед изменением схемы делать резервную копию.
- Миграции должны быть идемпотентными и выполняться при старте.
- Не удалять пользовательскую историю, память, события и настройки без явного требования.
- Новые запросы к данным размещать в `src/infrastructure/database/index.js`, а не в platform-коде.

Основные категории данных: сообщения и участники чатов, явная память, досье, настройки стиля/активного общения, rate limits, события и источники, состояния фоновых задач.

## V51: связь `active_chat_enabled` с фоновым поведением

`active_chat_enabled` является главным persisted-флагом всех автономных веток. Строка может попасть в выборку `getDueCommunicationSettings` и в перенос расписания 1–60 минут только при значении `1`. При выключении `next_outburst_at`, счётчик и время последнего автономного ответа сбрасываются, а связанные строки `communication_banter_state` удаляются. На старте `cleanupDisabledCommunicationAutonomy()` очищает stale-состояния, оставшиеся после старых версий.

## V97: `coords_override_settings`

Таблица `coords_override_settings` содержит одну глобальную строку `id=1`:

- `message_text` — дословный текст ответа;
- `enabled` — master switch специальной выдачи;
- `updated_by`, `updated_at` — последний владелец/момент изменения.

`корды сообщение` выполняет upsert текста и автоматически ставит `enabled=1`. `корды отключить` меняет только `enabled=0`, поэтому текст можно сохранить. `корды удалить` очищает `message_text` и одновременно выключает режим. Схема создаётся идемпотентно при старте и не требует удаления существующей базы.



## V99: одноразовая миграция анонса и координат

Добавлена общая таблица `bot_code_migrations` для продуктовых миграций, которые должны применяться к существующей `bot.sqlite` ровно один раз.

Миграция `events-v99-party-and-coords-2026-08-22`:

- заменяет канонические `party_date`, `party_format`, `party_info` на единый анонс «Случайное Пересоздание»;
- обновляет legacy-строки `dm_faq_answers` тех же тем;
- записывает `51.691730, 39.251385` в `coords_override_settings` и включает режим;
- после успешного применения пишет marker в `bot_code_migrations`.

Поэтому первый запуск V99 принудительно устанавливает запрошенные координаты, а следующие перезапуски уже не перетирают изменения, сделанные owner-командами.

## V103: non-destructive event dedupe registry

Добавлены таблицы `event_dedupe_groups` и `event_dedupe_members`. Они хранят результат последней глубокой дедупликации отдельно от сырых event-таблиц. `event_dedupe_groups.canonical_json` содержит полную canonical-карточку, включая поля, которых нет в raw schema (`displayDate`, `eventDays`, `mergedSources`), а `event_dedupe_members` связывает конкретные `source_type + event_id` с группой и ролью `canonical`/`duplicate`.

Сырые `telegram_events`, `vk_events`, `vk_chat_events`, `manual_events` при dedupe не удаляются и не получают `ignored`. Это сохраняет source evidence для следующих пересборок и предотвращает потерю многодневных расписаний или уникальных деталей разных источников. Registry разделён по `scope`: `all-db` для явной owner-команды и `configured` для обычной verified афиши.

## V104: `event_proposals` и ремонт существующей афиши

`event_proposals` хранит пользовательские заявки отдельно от опубликованных событий: submitter/platform, исходный текст, canonical source URL, подготовленный `parsed_events_json`, статус `pending|approved|rejected|auto_approved`, время отправки/истечения и данные модератора. Pending-заявка автоматически публикуется после 24 часов без owner-решения.

Mass-reparse не создаёт отдельную теневую таблицу: он повторно получает данные source URL и обновляет соответствующую строку `telegram_events`, `vk_events`, `vk_chat_events` или `manual_events` через единый DB helper, после чего пересобирается dedupe registry/snapshot. Неоднозначные URL, на которых сохранено несколько разных событий, автоматически не перезаписываются.

При подтверждённом обновлении manual URL прежние активные строки той же ссылки переводятся в `ignored`, а новая reparsed-карточка сохраняется как `approved`. Это сохраняет evidence и одновременно исключает старую карточку из публичной афиши.


## V108: `qr_code_settings`

Одна глобальная строка `id=1` хранит `message_text`, относительный `image_path`, `updated_by` и `updated_at` для QR-кода поддержки. `updateQrCodeSettings()` использует `NULL` как семантику «оставить текущее поле без изменений», поэтому замена текста не сбрасывает QR-картинку и наоборот. Сами бинарные данные изображения в SQLite не кладутся; файл находится в `data/qr-code/`.

## V118: `ai_runtime_modes`

`ai_runtime_modes` — рабочий реестр только успешно прошедших live-аудит комбинаций AI. Поля: provider, env_name, masked_key, model, capability (`text`/`image`), endpoint, tested_at. Секреты ключей в SQLite не сохраняются. Команда владельца `Гигорейв тест всех моделей` после полного успешного прохода атомарно очищает эту таблицу и записывает только успешные комбинации; таким образом нерабочие режимы сразу исчезают из рабочего реестра.


## V123: `pinball_scores` (legacy с V139)

V139 не запускает и не показывает Pinball, но таблица намеренно не удаляется, чтобы не разрушать старые данные. Исторически она хранит подтверждённые сервером результаты Telegram Mini App: Telegram user id/username/display name, score, duration, max combo/multiplier, число bumper/ramp/jackpot/multiball/nudge событий и timestamp. Секреты Telegram и raw `initData` в таблицу не записываются. Leaderboard выбирает лучший результат пользователя, сортирует по score DESC и при равенстве по времени записи.
