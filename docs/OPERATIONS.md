# Эксплуатация и диагностика

## Один экземпляр

При старте создаётся:

```text
data/vk-ai-bot.pid
```

Если процесс с PID жив, второй экземпляр завершается. Если lock остался после аварии, код проверяет PID и удаляет устаревший файл.

Не обходить блокировку ручным удалением, пока старый Node-процесс ещё работает.

## Нормальный старт

Минимальные признаки:

```text
[BOT PATCH] events-v52-reply-target-analysis
Имя бота: гигорейв
GPT router подключён...
[TELEGRAM BOT STARTED] ...       # необязательно
Запускаю VK Long Poll…
Бот запущен...
[SCRAPER MANUAL MODE] ...
```

## Важные логи

| Лог | Значение |
|---|---|
| `[GPT ROUTE]` | Тип запроса, режим, локальная/модельная астрология |
| `[GPT ROUTE RESOLVED]` | Фактический model id |
| `[GPT FINISH]` | Нормальное завершение stream |
| `[GPT USAGE]` | Токены |
| `[GPT STREAM CAPACITY RETRY]` | Модель перегружена, выполняется повтор |
| `[GPT UNKNOWN TERMS]` | Найденные и разрешённые термины |
| `[MANUAL EVENT LINK OPENED]` | Страница открыта, считан текст, вкладка оставлена |
| `[STRICT EVENT CLEANUP]` | Одноразовая очистка ложных событий |
| `[COMMUNICATION STYLE UPDATED]` | Новая теплота/роль |
| `[ACTIVE COMMUNICATION UPDATED]` | Включение/выключение 1/10 |
| `[COMMUNICATION OUTBURST ...]` | Фоновый выкрик |
| `[BOT PATCH]` | Проверка реально запущенной версии |

## GPT: `currently at capacity` и `terminated`

Это разные этапы одной сетевой проблемы:

1. upstream начинает SSE-stream;
2. модель сообщает capacity;
3. бот повторяет запрос;
4. socket может закрыться как `UND_ERR_SOCKET` / `terminated`;
5. пользователь повторяет запрос позже — новое соединение может успешно завершиться.

Это не означает переход на нестриминговый режим. Нормальный stream определяется `[GPT FINISH] reason=stop`.

При сетевой ошибке лимит запроса должен возвращаться пользователю.

## Браузер

- По умолчанию `SCRAPER_BROWSER_HEADLESS=0`.
- Используется persistent context и сохранённая авторизация.
- Страница ручного события после открытия не закрывается.
- VK-беседы не открываются при старте.
- После ручного закрытия вкладка не должна самопроизвольно переоткрываться старым retry-циклом.

Если браузер не найден, указать полный `SCRAPER_BROWSER_EXECUTABLE_PATH`.

## События

Если корректная страница не добавляется, проверить:

1. дата события не прошла;
2. дата относится к событию, а не публикации/предзаказу;
3. на странице есть конкретная площадка;
4. текст страницы действительно считан (`textChars > 0`);
5. evidence содержит отдельные подтверждающие фрагменты;
6. URL не ведёт на страницу сообщества без конкретного поста, если нужный анонс не виден в считанном тексте.

Если событие прошло, правильная диагностика: «распознано, но не добавлено в будущую афишу».

## Обновление патчем

1. Остановить процесс.
2. Скопировать `data/bot.sqlite`.
3. Распаковать patch поверх проекта.
4. Не заменять `.env` и `data`.
5. Выполнить `pnpm verify`.
6. Запустить `pnpm dev`.
7. Проверить `[BOT PATCH]`.
8. Проверить `/id`, помощь, базовый GPT и одну команду афиши.

## Восстановление

Если новый патч не запускается:

1. сохранить новый лог;
2. вернуть предыдущие изменённые файлы либо распаковать предыдущий полный source archive;
3. вернуть backup базы только если миграция действительно повредила данные;
4. выполнить `pnpm check:imports` и `pnpm check:syntax`;
5. проверить отсутствующий модуль в первой строке `ERR_MODULE_NOT_FOUND`.

## Деплой

Для текущего проекта достаточно:

- один VPS;
- один Node.js-процесс;
- systemd, PM2 либо один Docker Compose service;
- volume для `data`;
- ежедневная копия SQLite;
- ротация логов.

Kubernetes сейчас не нужен. Несколько реплик без переработки дадут двойные ответы, конкурирующие Telegram offsets, дубли фоновых задач и проблемы SQLite.

## Переход V40 → V41 через patch-архив

Zip не удаляет старые плоские тесты. После распаковки V41 поверх V40 один раз выполнить:

```bash
pnpm migrate:v41-layout
```

Скрипт удаляет только перечисленные старые `tests/*.test.mjs`; рабочий код, `.env` и `data` он не трогает. Полный source archive V42 уже имеет чистую структуру и в миграции не нуждается.


## Логи восстановления GPT V47

- `[GPT DELAYED RETRY]` — первая временная ошибка, указана модель и фактическая задержка 5–30 секунд.
- `[GPT MODEL ADVANCEMENT FALLBACK]` — вторая временная ошибка и переход к следующей доступной модели.
- `[GPT MODEL LIST REFRESH ERROR]` — `/models` недоступен; используется следующий настроенный уровень.
- `[BOT IDENTITY PROVOCATION] ... memoryBlocked=true` — обзывание бота перехвачено до памяти.


## Ручной запуск парсеров V63

Проверить каталог источников:

```text
Гигорейв парсер
```

Запустить всё:

```text
Гигорейв парсер
Гигорейв парсер tg:kurazhcity
Гигорейв парсер все
```

Оркестратор запускает источники последовательно. Публичный источник завершает проход до перехода к следующему; VK-chat источник открывает ручную сессию и возвращает управление. Итог содержит отдельный результат каждого источника. Команда owner-only и не заменяет ручную проверку открытых вкладок.


## Telegram connectivity recovery (V65)

При старте Telegram получает три попытки подключения. Если `api.telegram.org` или `t.me` сбрасывают TLS/соединение, VK продолжает работу, а повторное подключение Telegram планируется каждые пять минут.

Owner-команда из VK:

```text
Гигорейв телеграм проверить
```

Она проверяет Bot API, публичный `t.me`, валидность токена через `getMe`, состояние webhook и выполняет одну попытку переподключения. Ошибки классифицируются как TLS reset, DNS, timeout, 401, 409, 429 или HTTP/API error. Токен в ответ и лог диагностики не включается.

Если одновременно падают `api.telegram.org` и `t.me`, причина находится в сети/VPN/TUN/HTTPS-фильтре, а не в обработчике сообщений бота.
