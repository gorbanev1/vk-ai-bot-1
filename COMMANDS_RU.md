# Gigorave V188.99 — команды афиши и служебные ключи

## Выдача и поиск

- `тусы`, `ближайшие тусы`, `тусы на этих выходных`, `тусы на неделю`, `тусы на месяц`, `тусы <дата>` — обычная афиша.
- `кратко тусы ...` / `тусы ... коротко` — компактная выдача.
- `тусы ключи` — список известных площадок и жанров/форматов.
- Поиск по площадке: `тусы Ливерпуль`, `тусы Тупик`, `тусы Мама Анархия`, `тусы Vavilon`, `тусы Сто Ручьёв`, `тусы дизель`, `тусы Diesel Bar`, `тусы Diesel Hall`.
- `тусы дизель` включает Diesel Bar и Diesel Hall; точные ключи Bar/Hall различаются.
- Поиск по metadata: `тусы rock`, `тусы русский рок`, `тусы black metal`, `тусы death metal`, `тусы deathcore`, `тусы screamo`, `тусы indie`, `тусы post-punk`, `тусы punk rock`, `тусы hardcore`, `тусы электроника`, `тусы rave`, `тусы DJ`, `тусы акустика`, `тусы авторская песня`, `тусы вечеринка`, `тусы квартирник`, `тусы folk`, `тусы reggae`, `тусы blues`, `тусы emo`, `тусы alternative`, `тусы industrial`, `тусы techno`, `тусы house`, `тусы hip-hop`, `тусы cover`, `тусы grunge`, `тусы nu-metal`, `тусы metalcore`, `тусы поэзия`, `тусы jam`, `тусы open mic`.

## Картинки и metadata — владелец

- `тусы метаданные картинок` — CSV-ревью event-картинок и Vision metadata.
- `тусы метаданные картинок заполнить` — явный Vision-backfill картинок без metadata + безопасная перепроверка привязок.
- `тусы картинки на ревью` — показать владельцу неоднозначные кандидаты; ответ номером закрепляет выбранную афишу.
- `тусы архив картинок сжать` — уменьшить только картинки прошедших событий и перевести их в WebP; картинки будущих событий не затрагиваются.

## Удаление и исправление — владелец

- `тусы удалить <название или часть>` — **мягкое удаление**. Поиск идёт по сырым текущим строкам SQLite, а не только по уже схлопнутой выдаче: точное название, подстрока, отдельное содержательное слово, участники и допускаемые опечатки. Если найдено несколько карточек — бот нумерует их.
- После списка: `удалить 1`, `удалить 2`, `удалить 1 2`, `удалить 123` — удалить одну или несколько выбранных карточек. В Telegram для номеров появляются кнопки. После удаления возвращается меню «Тусы», pending-режим очищается и следующие команды не блокируются.
- `тусы удалить насовсем <название или часть>` — тот же расширенный поиск/выбор, но **постоянное удаление**. В SQLite сохраняется fingerprint: точная дата + содержательная идентичность названия/участников + площадка + source lineage + текст/evidence + poster Vision metadata + event tags. Такой event отсекается до повторной записи при parser/reparse.
- `тусы исправить <название или часть>` — найти карточку тем же расширенным поиском. Если совпадений несколько — выбрать `исправить 1` / `исправить 2`. После выбора можно прислать новый текст, правильную афишу картинкой или текст + картинку одним сообщением. Новая картинка заменяет старую только после Vision-проверки по дате/событию.
- `тусы исправить` — двухшаговый режим: сначала прислать название/часть названия, затем выбрать карточку (если нужно), после чего прислать текст и/или картинку. Если текстовая правка меняет дату/идентичность события, а старая афиша больше не совместима, она сохраняется в архиве, но перестаёт показываться.
- `тусы удаленные насовсем` — список активных permanent fingerprints.
- `вернуть тусу <название или #id>` — отключить permanent fingerprint; после будущего parser/reparse событие снова может появиться.
- `чёрный список тус` — аудит permanent fingerprints и старых legacy title-only записей. Legacy JSON rules больше не фильтруют выдачу и не блокируют перепарсинг.

## Проверка/перепарсинг — владелец

- `тусы проверить` — полный verified snapshot/dedupe.
- `тусы дубли проверить` — dry-run дедупликации.
- `тусы дубли статус` — статус проверки.
- `тусы дубли применить` — сохранить canonical/duplicate registry.
- `тусы перепарсить ссылки` — явный reparse ссылок будущих событий.
- `проверить тусы на совпадения` — диагностический аудит configured sources.

## Инварианты V188.99

1. Автоматическая и owner-замена source-афиши разрешена только после metadata/Vision-проверки; сомнение не превращается в случайную картинку. После owner-правки даты/названия старая афиша повторно проверяется и при несовместимости не показывается.
2. День+месяц — обязательный hard-сигнал poster→event; `15 сентября`, `15.09`, `15 September` и варианты с годом нормализуются к одному дню. Но **одной даты недостаточно**: выбранная картинка обязана дополнительно доказать идентичность через содержательное название/участников.
3. Название/участники — обязательная event-specific идентичность для публичной картинки; generic слова (`party`, `концерт`, `bar`, `club`, `DJ`, `rock` и т. п.) сами совпадение не создают. Старый V188.93 `date-only-source-poster` больше не является публично безопасной привязкой.
4. Одна календарная афиша может принадлежать нескольким child-events, если metadata картинки содержит соответствующие даты.
5. В multi-announcement текст делится последовательно по датам; Vision metadata картинки сохраняются, но не определяют число текстовых карточек.
6. Owner-manual карточка после первого сохранения не переписывается автоматическим reparse; обе операции удаления работают и для owner-manual событий.
7. Старые event migration/startup repair V188.67–V188.86 больше не запускаются автоматически при импорте/старте.
8. Прошедшие события из SQLite автоматически не удаляются; исторические картинки сжимаются только явной owner-командой.

9. Любая картинка в публичной карточке должна иметь конкретный `poster_image_index`, сохранённые Vision metadata именно выбранного изображения и `fact.imagePath`, который **точно совпадает с реально renderable path** карточки. Старый статус (`exact_poster_match`, `legacy_manual_poster`, `verifiedImagePaths`) без metadata или с metadata от другого файла больше не является обходом проверки: такая карточка выводится без картинки до явного backfill/review.
10. Основной dedupe выбирает каноническую карточку по релевантности и качеству metadata выбранной афиши, а не по порядку источников. Финальный asymmetric metadata-anchor sweep может поглотить несколько unsafe/stale вариантов одной тусы вокруг одного безопасного канона; карточку с собственной безопасной афишей он не поглощает. После merge остаётся максимум одна реальная source-афиша, заново проверенная против уже объединённой карточки.
11. Устаревшая duplicate-карточка не возвращается в verified snapshot через orphan-safety path: если raw-row детерминированно совпадает с уже каноническим событием, она помечается в аудите как `orphan-duplicate-suppressed` и не попадает в публичную выдачу. Сырая строка SQLite при этом не удаляется.
12. Явно разные физические площадки остаются защитным контуром: DIESEL Bar/Hall и конфликтующие номера домов никогда не склеиваются. Для разных названных площадок V188.99 допускает supersession только в safe-vs-unsafe случае, когда безопасная выбранная афиша сама содержит venue metadata, подтверждающие текущую площадку; две independently-safe карточки на разных площадках остаются разными.
13. В `Вообще все тусы` сохраняется приоритет QTickets из V188.88. Если QTickets-карточка заимствует афишу у дубля, вместе с путём переносятся selected Vision metadata и выполняется строгая повторная проверка against QTickets event; нерелевантная картинка не переносится.
14. Автоматический сетевой metadata-backfill при старте не возвращён. Для старых картинок без metadata используется только явная owner-команда `тусы метаданные картинок заполнить`, как в V188.92.

15. Owner-поиск `тусы исправить`/удаление сохраняет raw-SQLite recall из V188.97, но перед показом нумерованного списка прогоняет найденные строки через deterministic canonical dedupe. Поэтому шесть сырых вариантов одной актуальной тусовки не должны превращаться в шесть пунктов меню; raw/source строки при этом не уничтожаются.

## Astra: поток и файлы (V188.102)

`Гигорейв astra max <запрос>` использует Responses SSE stream. Если Astra создаёт файл через Code Interpreter, бот скачивает артефакт из OpenAI container и отправляет его обратно в Telegram документом. Входящие файлы Telegram передаются Astra как first-class `input_file` / `input_image`.


## Потоковые ответы всех GPT-router моделей (V188.103)

Все текстовые модели OpenAI-compatible runtime поддерживают оба транспорта: `stream` и `non-stream`. Для reasoning `high`, `xhigh` и `max` приоритет всегда у `stream`; если поток нельзя открыть до первого видимого delta, бот один раз пробует `non-stream` той же модели и только потом переходит к failover по ключам/провайдерам. Для `low`/`medium` сохраняется runtime/env предпочтение, но противоположный транспорт остаётся fallback.

В Telegram потоковые deltas теперь показываются пользователю постепенно: бот создаёт сообщение после первых данных и затем обновляет его через `editMessageText` с throttling, а не ждёт `response.completed`. Длинные ответы разбиваются на несколько сообщений. Финальный ответ переиспользует уже созданные stream-сообщения, поэтому второй полный дубль не отправляется.

Настройки throttling:

- `TELEGRAM_STREAM_FIRST_FLUSH_MS` — первая публикация, по умолчанию 300 мс;
- `TELEGRAM_STREAM_EDIT_INTERVAL_MS` — минимальный интервал обновлений, по умолчанию 900 мс;
- `TELEGRAM_STREAM_MIN_DELTA_CHARS` — минимальный прирост текста для планирования очередного edit, по умолчанию 72 символа.

Если поток уже успел показать пользователю часть ответа и затем оборвался, бот не запускает молча новую генерацию на другой модели/провайдере: это защищает от смешивания двух разных ответов в одном Telegram-сообщении.
