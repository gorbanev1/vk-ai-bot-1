GIGORAVE V188.45 — FIXED INTRADAY SUMMARY MEMORY + SUMMARY-FIRST CHAT ANALYSIS

Главное
=======
V188.45 закрывает два независимых источника лишнего расхода токенов:

1) Старый контур analyzeAllChatMessages() действительно прогонял всю сохранённую
   переписку через LLM чанками. Это был реальный full-raw sweep, а не просто
   неудачная надпись в интерфейсе. Он заменён на summary-first анализ.

2) Авторезюме переведено на один фиксированный календарь и новый immutable
   промежуточный слой batch -> day -> week -> month.

Фиксированные внутридневные батчи
================================
Единственные границы авторезюме:

  09:00  = 00:00–09:00
  13:00  = 09:00–13:00
  15:00  = 13:00–15:00
  18:00  = 15:00–18:00
  21:00  = 18:00–21:00
  23:59  = 21:00–24:00

В 23:59 публичный выпуск строится по материалу, доступному к моменту запуска.
Сообщения последней минуты 23:59–24:00, если появились после этого запуска,
становятся immutable delta revision и попадают в дневной rollup в 00:00; уже
оплаченный материал повторно в AI не отправляется.

Произвольные старые режимы day/evening/custom больше не меняют runtime-календарь.
Даже сохранённые legacy-настройки при вычислении времени принудительно используют
один fixed schedule. Legacy scheduler по-прежнему выключен по умолчанию.

Публичная отправка и внутренняя память
=====================================
Новая команда:

  резюмирование вкл
  резюмирование выкл
  резюмирование статус
  резюмирование сейчас

Старое слово «авторезюме» остаётся алиасом.

В новых чатах публичная отправка по умолчанию выключена. Настройка хранится в
SQLite и переживает перезапуск процесса. Если отправка была включена раньше, она
продолжает работать после restart без повторной команды.

ВАЖНО: внутренние summary-батчи строятся независимо от публичной отправки — для
всех сохранённых групповых peer, которые обнаружены в БД. Поддержано обнаружение
как VK group chats, так и Telegram group/supergroup через platform_identities.

При включённой публичной отправке в чат уходят ТОЛЬКО шесть fixed intraday
выпусков. Daily/weekly/monthly являются внутренней памятью и не создают лишний
спам в 00:00/воскресенье/конец месяца.

Накопительная иерархия
======================
Новый конвейер:

  raw message
      -> immutable intraday batch
      -> daily summary
      -> weekly segment
      -> monthly summary
      -> all-time composition

Отдельная durable SQLite-таблица hierarchy_batch_summaries добавлена к отдельным
таблицам daily / weekly / monthly.

Daily строится ТОЛЬКО из batch summaries.
Weekly строится ТОЛЬКО из daily summaries.
Monthly строится ТОЛЬКО из weekly-layer summaries.

Для недели, пересекающей месяц, weekly layer режется на month segments, поэтому
месяц остаётся календарно корректным и при этом не читает daily/raw напрямую.

Late/recovery сообщения
=======================
Уже оплаченное raw-сообщение не резюмируется повторно.

Coverage state остаётся immutable. Recovery-копия того же сообщения может быть
привязана к уже оплаченному coverage по нормализованным sender + timestamp + text.
Два разных native cmid одного источника не схлопываются только из-за одинакового
текста — это защищает реальные повторные сообщения.

Поздно найденное старое сообщение создаёт только новый batch delta, затем новый
непоглощённый daily delta -> weekly delta -> monthly delta. Старые raw/batch/day
ревизии не открываются заново.

Запросы по большим диапазонам
=============================
Для произвольного большого диапазона (например, «резюмируй последние 7000
сообщений») planner сначала покрывает диапазон наиболее крупными полностью
входящими уже готовыми блоками:

  month -> week -> day -> batch -> raw boundary tails

Пример:
  [кусок дня A] + [целый день B] + [целый день C] + [кусок дня D]

В LLM идёт:
  raw tail A + summary B + summary C + raw tail D

а не весь raw-корпус.

Если exact boundary tails всё ещё слишком велики, planner сначала использует уже
оплаченные overlapping batch summaries. Это может слегка расширить контекст на
границе, но не увеличивает raw-input.

Жёсткий raw-предел
==================
SUMMARY_USER_RAW_MESSAGE_HARD_LIMIT = 3000.

Это общий safety/cost circuit breaker для обычных runtime-путей. В V188.45 нет
ни одного намеренного owner bypass: даже владелец не может случайно прогнать
>3000 raw-сообщений через новый summary/database path. Это строже исходного ТЗ и
сделано намеренно до появления отдельного двухшагового owner-confirmation UX.

То есть owner-confirmation для >3000 raw В ЭТОЙ ВЕРСИИ НЕ РЕАЛИЗОВАН. Если он
понадобится, его следует добавлять отдельной explicit-командой с оценкой токенов,
а не ослаблять этот guard скрыто.

Full-chat database analysis — исправление главной дыры
======================================================
Старый analyzeAllChatMessages() раньше:

  getAllMessages -> format transcript -> split by chars -> LLM для ВСЕХ chunks

То есть 45 242 сообщения действительно могли последовательно пройти через AI.

Теперь:

  SQLite scan/count/search всей базы (локально, без LLM)
      + accumulated all-time summary memory
      + только ещё не покрытый raw tail (max 3000)
      -> LLM

Фраза «Проанализирована вся база ...» удалена. UI теперь отдельно сообщает:
- сколько сообщений просмотрено/найдено локальной БД;
- сколько накопленных summary-блоков использовано;
- сколько raw-сообщений реально передано в AI.

Команда «резюмируй всю историю» также использует all-time memory + bounded
непокрытый tail, поэтому текущие новые сообщения не теряются, но full raw history
никогда не открывается заново.

Поиск по всей базе
==================
Полный SQL/search scan разрешён: поиск может найти хоть десятки тысяч сообщений.
Но direct LLM evidence принудительно ограничивается 3000 найденными raw-сообщениями.
Интерфейс различает «найдено поиском» и «передано в ИИ».

Анализ участника
================
Поиск собственных сообщений и упоминаний выполняется по всей локальной базе, но
raw-бюджет одной такой операции разделён:

  до 2000 собственных сообщений участника
  + до 1000 сообщений из контекстных окон упоминаний
  = максимум 3000 raw

Это исключает второй скрытый обход лимита через два независимых анализа по 3000.
