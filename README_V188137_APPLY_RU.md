# Gigorave V188.137 — отдельный полный журнал парсинга и афиш

Этот накопительный ZIP — КОД поверх существующего проекта Gigorave; в него входят предыдущие изменения V188.130–V188.136 и новая диагностика V188.137. Архив не содержит `data/`, `.env`, ключей, базы SQLite, сохранённых картинок или рабочих логов; он ничего из них не удаляет. Реальная установка на компьютере владельца не выполнялась.

## Применение

1. Дождаться завершения текущих запросов/парсинга; не обновлять процесс во время активного задания. Сделать копию проекта и отдельно `data/`, `.env` и БД/WAL/SHM. Остановить бот.
2. Распаковать ZIP **в корень действующего проекта** с заменой программных файлов. Не подменять рабочие `data/` и `.env`, не удалять старые изображения или записи в БД.
3. При необходимости запустить `npm run test:v188137`, затем бот штатным способом.
4. Запустить **один обычный ручной парсинг**. Исправление не меняет логику выбора афиш и не выполняет массовую повторную загрузку; оно наблюдает, что действительно извлечено и почему выбрано/отброшено.

## Где искать результат

У каждого нового запуска есть постоянный каталог:
`data/parser-forensic-archives/<runId>/`
Он намеренно ВНЕ `data/logs`: встроенная очистка временных логов при смене сборки может удалить `data/logs`, но не эту папку. НЕ запускать ручную очистку `parser-forensic-archives` до сохранения диагностики.

Основные файлы:
- `trace.jsonl` — существующий детальный маршрут DOM/AI/источников/кандидатов; `*.dom.html` и `*.dom-state.json` — снимки DOM, исходный HTML, расположение и видимость изображений.
- `*.raw-cache.json` — все исходные посты/сообщения с полным содержимым, извлечённые парсером, включая отвергнутые при предфильтре.
- `poster-forensics/events.jsonl` — отдельный журнал ВСЕХ записанных этапов: исходные посты до/после VK API hydration, полные тексты, `imageUrls`, исходная DOM/media metadata, решения предфильтра, причины пропуска, Vision/постер-матчинг, принятые и отвергнутые события, старое и новое состояние БД, точные изменения полей/путей картинок при перепарсинге. Все источники из raw-cache попадают также в `source.raw-captured`; детальный before/after записи БД пока реализован на ветке VK-public.
- `poster-forensics/image-manifest.jsonl` — для каждой найденной локальной картинки исходный и сохранённый путь, размер, SHA-256, размеры изображения, состояние `copied`, `missing-on-disk`, `oversize-no-copy`, `outside-data-directory` или `copy-error`.
- `poster-forensics/images/` — копии **фактически существовавших локальных исходных файлов изображений** размером не более 20 МБ на файл. Уже сохранённая картинка копируется один раз по хешу, а не на каждом этапе. URL удалённой картинки фиксируется даже если скачать её во время парсинга не удалось; невозможных для клиента байтов изображения журнал не выдумывает и не делает дополнительных сетевых загрузок.
- `poster-forensics/final-announcement-cards.jsonl` — ПОЛНОЕ содержимое каждой карточки финального verified-снимка плюс факты выбора/отклонения афиши и наличие локального файла. `final-visibility-audit.json` — итоговая отчётность о видимости и dedupe (ограничения количества строк наследуются от существующего отчёта).
- `run-manifest.json` — пути к исходным диагностическим артефактам, включая постоянную папку `poster-forensics`.

Отдельно, при **реальном запросе карточек** после парсинга:
`data/event-poster-delivery-archives/YYYY-MM-DD.jsonl` — по каждой запрошенной карточке проверка наличия и привязки афиши, выбранный путь, попытка загрузки изображения, `uploadErrors`, результат фактической отправки: `card-sent-with-poster`, `card-sent-text-only`, `card-withheld-upload-failed`, `card-send-error`. Это НЕ то же самое, что итоговый снимок в БД: наличие картинки в БД не гарантирует её фактическую отправку в VK или Telegram.

## Как исследовать пропавшие картинки

Для одной проблемной афиши найти исходный пост по `sourceUrl`/`itemId` в `poster-forensics/events.jsonl`, сравнить `vk.dom-post-captured` → `vk.post-after-hydration` → `vk.prefilter-decision` → `vk.forensics.before-db-write` → `vk.forensics.after-db-write` → `final-announcement-cards.jsonl` → фактическую попытку отправки в `data/event-poster-delivery-archives`. Идентификатор события, дата и источник связывают этапы. Пропажу можно отличить от отсутствия исходной ссылки, ошибки скачивания, несоответствия Vision metadata, строгой безопасности привязки к конкретному файлу и ошибки загрузки вложения.

## Ограничения и безопасность

Логи записывают только наблюдаемые данные. Если браузер не увидел скрытую VK-картинку или загрузка удалённого URL не состоялась, её байты получить из воздуха невозможно. Журналы и копии изображений **могут занимать много места** и содержать полный текст постов, изображения, URL и данные участников; хранить локально, доступ ограничить, не публиковать без проверки приватных полей. При ошибке записи диагностики код отдельно пишет `[PARSER POSTER FORENSICS WRITE ERROR]` либо `[EVENT POSTER DELIVERY FORENSICS WRITE ERROR]`, не маскируя её под отсутствие изображения.

Это изменение **не исправляет автоматически** уже пропавшие картинки. Оно даёт данные для точного исправления после следующего запуска парсинга и получения тех анонсов, у которых нет изображения.
