Gigorave Bot V140 — existing-source refresh + no-hang proposal path
Build: events-v140-existing-source-refresh-no-hang
Package: 0.140.0

WHY
1. “➕ Предложить тусу” treated a URL that was already saved in the event database as a new proposal instead of an update.
2. For an exact VK wall URL the bot could already obtain the post through wall.getById, but then still opened the Playwright page. A blocked/manual VK page could wait for many minutes even though the API had already returned the post text and poster.
3. Proposal image/strict extraction reused the global 15-minute OpenAI timeout, so an AI call could make the Telegram dialog look frozen.
4. Even after a row was updated, waiting synchronously for the full verified-snapshot rebuild could again block the reply because that rebuild can normalize/summarize the whole event database with AI.
5. Old saved event rows could therefore remain without a poster although their exact source post already contained one.

FIXES
- Canonical source identity is checked across telegram_events, vk_events, vk_chat_events and manual_events before owner proposal parsing.
- If the owner submits an exact VK wall URL that already exists, V140 refreshes the existing stored row(s) in place. It does NOT create a new proposal or duplicate.
- The refresh obtains the exact post via VK wall.getById, re-parses the fresh announcement, and merges fresh non-empty fields over the old row while preserving useful old fields that the fresh parser did not recover.
- Missing imagePaths are repaired from the source post. The VK API image list is already poster-ranked; the refresh downloads only the best real poster and does not synthesize a placeholder for this repair path.
- Poster download is bounded (20 s per direct repair candidate; one candidate) and public image download first uses direct HTTP before a browser-request fallback.
- Exact VK wall proposal parsing skips Playwright page opening completely after successful API hydration.
- Browser navigation/manual-access fallback for proposal links is bounded to 45 s instead of the former long manual wait.
- Proposal-specific vision/text AI calls use a dedicated bounded timeout (default 45 s; configurable) rather than the global 15-minute generation timeout.
- After an in-place source refresh the old verified snapshot is invalidated immediately. The full rebuild is queued in the background, so the Telegram reply does not wait for database-wide AI work. Until rebuild completion, event output uses the deterministic DB fallback and sees the refreshed row.
- A normal user proposal that is later approved/auto-approved and has the same canonical source also updates the existing row instead of adding a duplicate.

NEW OPTIONAL ENV
EVENT_SOURCE_REFRESH_TIMEOUT_SECONDS
  Exact VK wall API fast-refresh budget. Default 15 s, clamped to 5..60 s.

EVENT_PROPOSAL_AI_TIMEOUT_SECONDS
  Vision/strict-extraction budget used by the proposal flow. Default 45 s, clamped to 10..120 s.

EXPECTED OWNER FLOW
1. Press “➕ Предложить тусу”.
2. Send the same VK wall URL that is already stored but has stale/missing data.
3. Bot says that the source already exists and is being refreshed.
4. Existing row is updated in place; no new proposal is created.
5. If VK source contains the poster and it downloads successfully, the existing event gets that real poster.
