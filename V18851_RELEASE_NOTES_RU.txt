Gigorave V188.51 — recursive media context для reply/repost/forward
=================================================================

Главный invariant
-----------------
Если изображение доступно из текущего сообщения, reply, repost, forward или любой
вложенной комбинации этих объектов, оно собирается централизованным media-context
до специализированного routing. Ошибка одного вложения не должна приводить к
молчанию всего пользовательского запроса.

1. Единый recursive media extractor
-----------------------------------
Добавлен collectIncomingMediaContext(...), который рекурсивно собирает:
• изображения текущего сообщения;
• reply;
• forward/fwd;
• repost/shared message;
• VK wall/copy_history, включая repost внутри repost;
• image-document;
• несколько изображений/страниц одного источника;
• text/caption каждого уровня.

Контекст сохраняет sourceMessageId, sourcePath, nestingDepth, attachment ID/type,
локальный индекс/количество изображений в источнике и глобальный operation order.

Технические защиты:
• visitedMessageIds;
• visitedAttachmentIds;
• WeakSet для object-cycle;
• дедуп по attachment ID и canonical URL до загрузки;
• дедуп по SHA-256 после загрузки;
• максимум 20 семантических уровней reply/repost/forward;
• максимум 512 traversed nodes и 64 изображения на операцию;
• depth/node/image limit фиксируется audit-event, а не скрытым обрывом.

2. Media enrichment до command/mode routing
-------------------------------------------
Входной pipeline теперь выполняет media enrichment до специализированного режима:

normalize update
→ recursively collect conversation/media context
→ hydrate доступные VK reply/wall payloads
→ analyze every discovered image
→ route command/mode
→ execute

Распознанный media-context централизованно попадает в обычный AI-ответ, vision,
summary/comment/search-like AI paths, document generation и другие text modes,
которые используют общий GPT prompt pipeline.

Image editor сохраняет старый правильный invariant: исходное изображение передаётся
как настоящий image edit target; vision/OCR context лишь дополняет edit instruction.

3. Каждая картинка анализируется отдельно и в порядке источника
---------------------------------------------------------------
Для каждого найденного изображения выполняется отдельный vision/OCR preprocessing:
• OCR text;
• visual description;
• content type;
• sourcePath/sourceMessageId;
• global order;
• local "image N of M" внутри конкретного сообщения/репоста.

После hydration локальная нумерация уточняется. Например, если webhook показал только
preview первой страницы, а wall hydration раскрыл 4 страницы, первая страница тоже
становится image 1 of 4, а не остаётся 1 of 1.

В AI-context отдельно передаётся TEXT/CAPTION CHAIN с путями каждого уровня, чтобы
caption вложенных reply/repost не терялся и фотографии разных источников не смешивались.

4. Partial failure больше не превращается в silent failure
----------------------------------------------------------
Media items обрабатываются последовательно и изолированно: ошибка одной страницы не
прерывает оставшиеся.

Если обработано 3/4, пользователь получает предупреждение вида:
  Обработано 3 из 4 изображений. Одно вложение не удалось получить; отвечаю по
  доступным материалам. ID операции: ...

При полном сбое вложений пользователь получает сообщение с operationId, а основной
routing всё равно продолжает работу по доступному текстовому контексту.

5. Полный media audit + forensic copy
-------------------------------------
Для media pipeline пишутся operation logs с полями:
botVersion, operationId, platform, chatId, messageId, sourceMessageId, sourcePath,
nestingDepth, attachmentId/type/index/count, URL/source reference, download state,
SHA-256, MIME, width/height, OCR state/result/error, vision state/model/ladder/duration,
timeout/retry и final status.

Forensic-каталог операции:
  data/audit/media/<operationId>/

Содержит:
• metadata.json;
• message-structure.json;
• pipeline.jsonl;
• errors.jsonl при ошибках;
• сохранённые найденные изображения;
• ocr.txt;
• vision.txt;
• results.json.

Секреты в URL/headers/keys редактируются перед записью forensic metadata/logs.

6. Дедупликация
---------------
Порядок дедупа:
attachment ID → canonical URL → SHA-256 скачанного файла.

Одинаковый файл, обнаруженный через reply/repost/quote или повторный CDN URL,
не анализируется повторно; результат OCR/vision переиспользуется в текущей операции.

7. VK hydration и совместимость диагностики
-------------------------------------------
Сохраняется hydration reply через messages API и wall/copy_history через wall.getById.
Старые диагностические markers, на которые опираются regression/static tests,
сохранены вместе с новым [VK RECURSIVE MEDIA CONTEXT].

8. Regression tests V188.51
---------------------------
Добавлены проверки:
• message → image;
• message → reply → image;
• message → repost → image;
• message → repost → repost → image;
• quoted/reposted 4-page guide: все 4 страницы найдены и упорядочены;
• image-document + caption;
• duplicate attachment/URL;
• cycle/depth-limit;
• 4 discovered / 3 processed / 1 failed: четвёртая страница всё равно обрабатывается;
• pre-route media enrichment, forensic logging и real edit target для image editor.

9. Сохранённые гарантии V188.48/V188.49
---------------------------------------
Не менялись operation supervisor, hard watchdog, stop/abort plumbing, non-blocking
Telegram/VK transport, model ladder/failover logging, summary memory/routing и
системная идентичность Гигорейва.
