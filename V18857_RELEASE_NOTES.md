# V188.57 — history completeness guard

По startup-логу V188.56 обнаружен реальный сценарий, который старый durable checkpoint не ловил:
`currentRows=51719 >= checkpointRows=51667`, поэтому local SQLite backup scan был пропущен,
но последующая удалённая сверка всё равно нашла `new=812`. Значит количество строк было больше
checkpoint, однако внутри истории существовали пропуски.

## Исправлено

- Durable local-history checkpoint v2 хранит fingerprint исторического покрытия, а не только row count.
- Проверяется набор CMID/содержимое до сохранённой границы. Новые сообщения в хвосте больше не могут
  маскировать старую дыру.
- Fingerprint учитывает inventory локальных SQLite snapshots. Новый healthy/corruption backup автоматически
  делает старый checkpoint невалидным и запускает повторную read-only сверку.
- Старые V187.2/V188.56 checkpoint автоматически считаются legacy: первый startup V188.57 обязательно
  заново просмотрит локальные snapshots и затем запишет checkpoint=v2.
- Чтение таблицы `messages` из backup выполняется `NOT INDEXED`, чтобы повреждённый вторичный индекс не
  мешал извлечь читаемые строки таблицы.
- Добавлена owner-команда полной удалённой сверки:
  `Гигорейв подтяни историю с самого начала` / `... всю` / `... полностью`.
  При CMID fallback она идёт newest-to-oldest вплоть до CMID 1 без временного cutoff.

## Что означает присланный лог V188.56

`new=812` — доказательство, что на момент старта активной БД не хватало как минимум 812 входящих сообщений
в проверенном недавнем диапазоне. Recovery их добавил. Этот факт сам по себе не доказывает отсутствие более
старых дыр, потому что local backup scan ошибочно был пропущен по count-only checkpoint.

V188.57 закрывает именно этот сценарий.
