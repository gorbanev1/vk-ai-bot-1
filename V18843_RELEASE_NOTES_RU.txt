Gigorave V188.43 — industrial immutable calendar summary rollup

ЧТО ИСПРАВЛЕНО

1. Model routing summary-контуров
- Единая лестница: default -> gpt54 -> gpt55 -> pro -> pro2 -> pro3 (Sol последний).
- На каждой логической модели максимум 2 технические попытки, затем переход выше.
- Не-техническая/контентная ошибка не является поводом прожигать всю лестницу.
- Для подозрительно короткого summary допускается ровно один quality-correction на той же реально сработавшей модели, без escalation. Если correction падает, используется первый ответ.

2. Убраны 100k+ raw summary requests
- Raw leaf budget по умолчанию: ~24k входных токенов.
- Merge payload по умолчанию ограничен 48k символов.
- inputTokenBudget теперь реально передаётся в leaf batching (не только логируется).

3. Старый raw autoresume scheduler выключен по умолчанию
- LEGACY_AUTO_SUMMARY_SCHEDULER_ENABLED=false по умолчанию.
- Старые 06:00/13:00/18:00 и другие пользовательские raw-слоты больше не стартуют автоматически параллельно календарному rollup.
- Для rollback совместимости можно явно выставить LEGACY_AUTO_SUMMARY_SCHEDULER_ENABLED=1.
- Команда "авторезюме сейчас" при выключенном legacy scheduler запускает безопасный calendar maintenance с immutable coverage вместо старого raw scheduler.

4. Immutable raw-message coverage
- hierarchy_message_state: ON CONFLICT(message_key) DO NOTHING.
- После успешного платного daily summary запись daily revision и message coverage происходит атомарно в BEGIN IMMEDIATE transaction.
- Recovery/migration copy с тем же нормализованным sender + timestamp + text, пришедшая из другого source peer, получает alias к уже оплаченному состоянию и не идёт в AI повторно.
- Два разных native cmid в одном source не схлопываются только из-за одинакового текста: это защита от false dedupe реальных повторных сообщений.

5. Отдельные таблицы календарного накопительного summary
- hierarchy_daily_summaries
- hierarchy_weekly_summaries
- hierarchy_monthly_summaries
- hierarchy_rollup_edges
- hierarchy_rollup_delivery

6. Календарный pipeline
raw message (ровно один платный вход)
  -> daily revision
  -> weekly month-segment revision
  -> monthly revision

Daily:
- строится после закрытия календарного дня, граница 00:00 local time.

Weekly:
- строится ТОЛЬКО из daily revisions.
- обычная неделя: Monday 00:00 -> next Monday 00:00.
- доставка: Sunday 24:00 / Monday 00:00.

Monthly:
- строится ТОЛЬКО из weekly-layer revisions.
- доставка: last day 24:00 / first day next month 00:00.

Почему weekly хранит month-clipped segments:
Календарный месяц может закончиться посреди Mon-Sun недели. Невозможно одновременно выполнить "month строго из weekly" и "month закрыть последнего числа", если weekly существует только целыми неделями. Поэтому weekly layer на границе месяца делится на неперекрывающиеся сегменты. Полное недельное сообщение собирается из сегментов, а monthly берёт только сегменты своего месяца. Raw/daily напрямую в month не попадает.

7. Late-message delta rollup
- Поздно найденное старое сообщение не пересчитывает старый день.
- Создаётся daily revision N+1 только по новому raw.
- Эта revision ровно один раз продвигается в weekly delta.
- Weekly delta ровно один раз продвигается в monthly delta.
- UNIQUE promotion edge не даёт повторно использовать старую daily/weekly revision.
- Старые уже доставленные day/week/month не спамятся повторной доставкой из-за late delta; delta сохраняется в накопительной памяти.

8. All-time summary
- Не читает заново raw history после calendar maintenance.
- Использует неперекрывающиеся слои:
  legacy paid base + monthly revisions + ещё не поднятые weekly revisions + ещё не поднятые daily revisions.
- Если у V188.42 уже есть paid leaf coverage, но процесс упал до сохранения legacy root, all-time использует сами paid legacy leaf summaries и не перечитывает их raw.
- Явный all-time может закрыть текущую дневную delta раньше полуночи; последующие сообщения этого дня становятся новой delta, старые raw не повторяются.

9. Durable/SQLite
- busy_timeout выставляется до WAL/migrations, чтобы параллельная инициализация меньше ловила SQLITE_BUSY.
- Daily summary + raw coverage атомарны.
- Weekly/monthly summary + promotion edges атомарны.

ЧТО СОЗНАТЕЛЬНО НЕ ДЕЛАЕТСЯ
- Исторические day/week/month rows не синтезируются задним числом из raw, уже оплаченного старым hierarchy: это нарушило бы правило never rebill. Старый paid hierarchy используется как legacy base, новые/непокрытые/late сообщения идут в календарные таблицы.
- Запуски очень старого legacy auto-summary, сделанные ДО появления immutable message ledger, нельзя надёжно привязать к каждому raw message только по таблице auto_summary_runs: там нет полного membership ledger. Код не угадывает это и не делает опасный fuzzy-dedupe. V188.42 hierarchy coverage, если она есть, переносится и соблюдается.
- Гарантия exactly-once относится к одному production bot process + общей SQLite state. При одновременном active-active запуске нескольких независимых bot processes они могут теоретически одновременно начать один и тот же AI request до DB commit; DB не допустит двойной commit, но upstream токены могут быть потрачены дважды. Для multi-instance deployment нужен отдельный distributed/DB lease до AI call.
