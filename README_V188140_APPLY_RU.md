# Gigorave V188.140 — один главный финальный DOM по каждому источнику в команде «парсер всё»

## Что изменилось

Для штатной ручной команды «парсер всё» (основной и второй пул) после **существующего** чтения и обработки DOM каждого источника выполняется отдельная подготовка страницы к финальному слепку. Для VK-стены направление — **вниз**, для VK-беседы — **вверх по реальному контейнеру истории** (используется существующий `scrollConversationUp` и механизм выбора скролл-контейнера); для публичной Telegram HTML-страницы — **вверх**, отдельный слепок каждой открытой URL-страницы с `beforeId`.

Подготовка не делает полных снимков HTML: выполняет шаги прокрутки, сохраняет только лёгкие показатели (позиция, высота, край), две контрольные догрузки, финальное ожидание. Если контроль вызвал догрузку/увеличение высоты, контроль начинается заново; выполнение ограничено числом шагов и проверок. По завершении **один раз** читается исходный `document.documentElement.outerHTML`, одновременно считываются состояние страницы, ссылки и метаданные ресурсов. HTML сохраняется без изменения; аналитическая структура — в отдельном файле. Файлы записываются во временные имена с `sync` и `rename`; `manifest.json` записывается последним.

На время обычного парсинга exact-контур по-прежнему читает HTML вкладки **в память**, потому что без него существующий парсер не работает. Но в режиме «парсер всё» его промежуточные HTML больше **не сохраняются на диск** в `vk-dom-fixtures`/помежуточные `*.dom.html`; предварительный baseline V188.139 в этом режиме также пропускается. Прочие виды запуска не изменены, старые пер-итерационные режимы продолжают поддерживаться. Исходные данные событий, фотографии и их отдельный forensic-журнал V188.137 по-прежнему записываются.

Важное ограничение: эта дополнительная подготовка выполняется **после** старого прохода и **не меняет список событий, уже извлечённых и принятых прежним парсером**. Сам текущий парсер ещё не переведён на офлайн-работу по `dom.raw.html`: это **вход для разработки нового точного контура**, а не новая схема извлечения. Если VK удаляет узлы старых постов при прокрутке, один конечный HTML их не вернёт. Если страница догружается бесконечно или достигнут лимит шагов, в `preparationStatus` будет `bounded-or-unstable`; слепок всё равно сохранится с явным предупреждением об ограниченной полноте.

## Где лежит эталонный вход

После команды ищи последний каталог:

```text
data/parser-forensic-archives/<runId>/
  trace.jsonl
  vk-dom-final-snapshots/
    vk-<source>-<hash>/              # публичная VK-страница
      dom.raw.html                   # ГЛАВНЫЙ HTML для первого точного контура
      page-state.json               # полный runtime-контекст и политика подготовки
      dom.structure.json            # подсказки по структуре, не готовый шаблон
      resources.json                # атрибуты и браузерные свойства изображений/ссылок
      pagination-progress.json      # шаги и контрольные проходы, направление, статус
      manifest.json                 # checksum/размер и список файлов
      PROMPT_FOR_DOM_AUDIT_RU.txt    # задание для анализа в другом чате
    chat-<peer>-<hash>/             # отдельная VK-беседа, scroll up
    tg-<channel>-before-<id>-<hash>/ # конкретная HTML-страница Telegram, scroll up
  poster-forensics/                  # прежний журнал анонсов и картинок
```

Новая папка появляется только при успешном захвате каждого источника. Если вкладка закрыта/снимок не удалось записать, смотри `vk.final-fixture.failed`, `vk.final-fixture.capture-error` либо `dom.final-fixture.capture-error` в `trace.jsonl`. Ошибка создания дополнительного слепка **не останавливает** исходный парсер и не удаляет его данные. Для Telegram HTML разные страницы `?before=...` имеют **отдельные** каталоги; один слепок не означает всю историю канала.

`preparationStatus=edge-confirmed-bounded` означает: в пределах лимита достигнут правильный край и прошли две контрольные догрузки. Это **не** означает гарантию полного архива публикаций. `bounded-or-unstable` — край/контроль не подтверждены до лимита: такой DOM нельзя выдавать за полный.

## Установка

1. Дождись окончания активного парсинга. Сделай резервную копию проекта и всей `data/`, в том числе SQLite/`-wal`/`-shm` и сохранённых афиш. Останови бот.
2. Распакуй **накопительный** архив V188.140 в корень проекта. ZIP содержит только код, тесты, инструкции, контрольные суммы — нет `.env`, БД, браузерного профиля, фотографий и личных логов. Сравни кодовые файлы с собственными локальными правками до замены.
3. Выполни `npm run test:v188140` и запусти бот штатным способом. Тесты проверяют мок-состояния/офлайн-проверку, **не** настоящую вкладку VK/Telegram.
4. Один раз запусти «парсер всё». После прохождения источника найди его каталог `vk-dom-final-snapshots/<source>/`.
5. Проверь HTML и весь каталог **офлайн**, из корня проекта:

```bash
node scripts/vk-dom-final-verify.mjs "data/parser-forensic-archives/<runId>/vk-dom-final-snapshots/<source>"
```

Для передачи сюда или в другой чат упакуй **конкретную папку источника целиком**, а не только JSON старого парсера. Важнейший файл — `dom.raw.html`; рядом обязательны `manifest.json`, `page-state.json`, `dom.structure.json`, `resources.json`, `pagination-progress.json`.

## Безопасность и границы

Полный DOM приватной VK-беседы/Telegram может содержать переписку, ссылки и чувствительные данные. Проверь содержимое **перед передачей**; не публикуй архив в открытом доступе. Если требуется удалить личные данные, делай для анализа отдельную копию и **не называй её исходным эталоном**: контрольная сумма исходного файла уже не совпадёт.

Не приписывай снимку доказанную полноту всей ленты или корректность ожидаемых анонсов: метаданные источника не подменяют содержимое HTML; `expected/announcements.json` и точный алгоритм создаются после проверки реального DOM.
